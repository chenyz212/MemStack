# 项目全局文档与结论卡片执行计划

## 1. 文档目的

本文档用于指导 MemStack 桌面客户端实现以下两项能力：

1. 为绑定本地工作空间的项目维护五份项目级全局文档，使新的 AI 会话能够快速恢复项目背景、有效决策、当前状态、活动问题和近期变化。
2. 在重大问题解决后生成结构化结论卡片，通过 MCP 提交为候选记忆，经用户审核后进入正式记忆、全文检索、可选 Embedding 和记忆图谱。

本文档是实施计划，不代表当前功能已经完成。开发时必须先核对仓库中的既有实现，复用现有项目绑定、候选记忆、乐观锁、归档、全文检索、Embedding 和图谱能力，避免建立重复逻辑。

## 2. 建设目标

### 2.1 项目现场恢复

新的 AI 会话进入本地项目后，只需调用一次项目交接工具，即可获得经过预算裁剪的项目现场，不再依赖用户重复讲解历史背景。

### 2.2 项目事实持续更新

五份 Markdown 正式文件是项目文档的唯一事实来源。MemStack 数据库只保存同步镜像和索引，负责检索、交接和异常恢复，不与本地文件形成两个可以独立修改的事实源。

### 2.3 解决经验复用

重大问题解决后，将可验证的根因、结论、失败方案、适用条件和下一步保存为结构化结论卡片。后续遇到相似问题时，可以通过 MCP 检索历史解决方案。

### 2.4 用户保持最终控制权

- 初始化内容必须逐份审核。
- 草稿允许用户直接编辑。
- 五份草稿全部批准后才创建正式文件。
- 结论卡片必须进入候选区，经用户确认后才成为正式记忆。
- 项目文档是否上传 Embedding 由用户按项目控制，默认关闭。
- AI 客户端提示词必须展示变更后由用户点击安装，不允许后台静默修改。

## 3. 非目标

本期不实现以下能力：

- 不为五份项目文档保存完整修订历史。
- 不把五份文档建模成五条普通记忆。
- 不为结论卡片生成本地 Markdown 文件。
- 不监听没有活动 MCP 会话的全部项目。
- 不扫描用户机器上的全部工作空间。
- 不要求项目文档提交到 Git。
- 不因初始化未完成、MCP 不可用或 Token 只读而阻断用户当前开发任务。
- 不依赖 AI 自觉维护文件来保证一致性，关键约束必须由 MCP 和桌面端校验。

## 4. 已确认的核心原则

### 4.1 事实来源

```text
正式 Markdown 文件：项目文档唯一事实来源
SQLite：正式内容镜像、唯一上一版快照、同步状态和检索索引
初始化草稿：正式创建前的待审核内容，不属于正式项目记忆
结论卡片候选：待用户确认的结构化解决经验
```

### 4.2 生效范围

只有同时满足以下条件时才启用项目文档能力：

1. 当前 MCP 会话能够确定本地工作空间绝对路径。
2. 当前工作空间已绑定 MemStack 项目。
3. 当前访问令牌对该项目具有相应读取或写入权限。

纯聊天、普通问答、没有本地工作空间的会话不得自动初始化项目文档。

### 4.3 写入边界

- AI 不得使用普通文件工具直接修改 `.memstack` 中的正式项目文档。
- AI 对正式文档的修改必须调用 MCP，由 MCP 完成版本检查、格式校验、文件写入和数据库同步。
- 用户可以在外部编辑器手动修改正式文件，文件监听器负责将变化同步回数据库。
- MemStack 中的正式文档查看界面保持只读。
- 初始化草稿可以在 MemStack 审核界面中编辑。

### 4.4 失败不阻断任务

当 MCP 不可用、令牌只读、数据库同步失败或草稿仍待审核时，AI 应继续完成当前项目任务，并明确提示：

```text
项目记忆未更新
```

不得将项目记忆故障伪装为写入成功。

## 5. 工作空间目录设计

### 5.1 最终目录

```text
<workspace>/.memstack/
├── drafts/
│   └── initialization/
│       ├── 01_CONTEXT.md
│       ├── 02_DECISIONS.md
│       ├── 03_CURRENT_STATUS.md
│       ├── 04_PROBLEMS.md
│       └── 05_CHANGELOG.md
├── 01_CONTEXT.md
├── 02_DECISIONS.md
├── 03_CURRENT_STATUS.md
├── 04_PROBLEMS.md
└── 05_CHANGELOG.md
```

如实现原子替换需要同目录临时文件，可在 `.memstack` 内使用内部暂存目录。内部目录名必须由常量统一定义，完成或恢复后清理，不允许进入项目交接内容和搜索索引。

### 5.2 路径语义

- `.memstack/drafts/initialization/`：唯一一套初始化草稿。
- `.memstack/*.md`：五份正式项目文档。
- 草稿永久保留，直到正式创建成功或用户主动删除。
- 正式创建成功后自动删除初始化草稿。
- 正式文件和草稿异常并存时，完整且校验通过的正式文件集合优先。
- 如果只存在部分正式文件，不得直接认定正式初始化成功，应进入晋升恢复流程，补齐并校验五份文件。

### 5.3 Git 忽略

检测到工作空间属于 Git 仓库时，在该仓库的 `.git/info/exclude` 中幂等写入：

```gitignore
/.memstack/
```

不得修改仓库的 `.gitignore`，不得产生需要用户提交的忽略规则变更。非 Git 工作空间跳过该步骤。

## 6. 文件格式与正文模板

### 6.1 YAML 头

五份正式文件和初始化草稿均使用同一组最小 YAML 字段，草稿或正式状态由所在路径决定：

```yaml
---
memstack: PROJECT_DOCUMENT
documentType: CONTEXT
schemaVersion: 1
---
```

`documentType` 只允许以下值：

- `CONTEXT`
- `DECISIONS`
- `CURRENT_STATUS`
- `PROBLEMS`
- `CHANGELOG`

以下易变字段只保存在数据库中，不写入 Markdown，避免同步写入反复触发文件监听：

- `projectId`
- `documentId`
- `version`
- `checksum`
- `updatedAt`
- `syncStatus`

### 6.2 `01_CONTEXT.md`

固定章节：

```text
# 项目背景
## 项目目标
## 核心范围
## 运行环境
## 技术栈
## 系统架构
## 数据存储
## 外部依赖
## 关键约束
## 待确认事实
```

只记录稳定的项目基本事实。无法从仓库确认的内容放入“待确认事实”，不得由 AI 猜测后当作事实保存。

### 6.3 `02_DECISIONS.md`

固定章节：

```text
# 项目决策
## 有效决策
## 已替代决策
```

决策编号使用 `DEC-日期-序号`，例如 `DEC-20260820-001`。每项至少包含：

- 决策内容
- 选择原因
- 备选方案
- 影响范围
- 决策日期
- 替代关系

旧决策不得直接删除。决策失效时移入“已替代决策”，并标记替代它的新决策编号。

### 6.4 `03_CURRENT_STATUS.md`

固定章节：

```text
# 当前状态
## 当前阶段
## 已完成
## 进行中
## 阻塞项
## 当前指标
## 下一步
## 待确认事项
## 最后核验时间
```

该文件只描述当前状态，不追加历史流水。状态发生变化时直接更新对应章节。

### 6.5 `04_PROBLEMS.md`

固定章节：

```text
# 项目问题
## 当前问题
## 已解决问题
```

问题编号使用 `PROB-日期-序号`，例如 `PROB-20260820-001`。当前问题至少包含：

- 严重程度
- 问题现象
- 影响范围
- 已有证据
- 已尝试方案
- 下一步

问题解决后从“当前问题”移入“已解决问题”，保留压缩摘要、解决日期和结论卡片 ID。详细解决经验保存在结论卡片，不在该文件重复保存大段排查过程。

### 6.6 `05_CHANGELOG.md`

按日期倒序追加有意义的项目变化，每项包含：

- 完成内容
- 产生影响
- 关联决策编号
- 关联问题编号

不得机械复制全部 Git 提交，不记录纯格式化、无行为变化的重构和无意义编辑。

## 7. 数据模型设计

实施前先检查现有迁移、模型和候选记忆结构，字段命名遵循仓库现有风格。以下是目标语义，不要求脱离现有模型机械照搬名称。

### 7.1 正式项目文档

建议新增 `project_document` 表：

```text
id
project_id
document_type
relative_path
content
checksum
version
previous_content
previous_checksum
previous_version
embedding_enabled
sync_status
created_at
updated_at
```

约束：

```text
UNIQUE(project_id, document_type)
```

要求：

- 每个项目每种文档类型只能有一份正式记录。
- 只保存当前版本和唯一上一版安全快照。
- `version` 每次成功写入后单调递增。
- `checksum` 基于规范化后的完整文件内容计算。
- `embedding_enabled` 由项目级设置控制，默认关闭。

### 7.2 初始化草稿

建议新增 `project_document_draft` 表：

```text
id
project_id
document_type
relative_path
content
checksum
version
review_status
approved_version
created_at
updated_at
```

约束：

```text
UNIQUE(project_id, document_type)
```

审核状态至少包括：

- `PENDING_REVIEW`
- `APPROVED`

编辑草稿后必须递增 `version`。如果新版本与 `approved_version` 不一致，审核状态必须恢复为 `PENDING_REVIEW`。

### 7.3 项目文档设置

在现有项目设置结构中增加：

```text
project_document_embedding_enabled
```

默认值必须在创建项目设置时由调用方显式传递为 `false`，不得依赖函数默认参数。开启前必须显示内容可能发送到当前 Embedding 服务的提示。

### 7.4 结论卡片

正式结论卡片继续使用普通记忆作为检索主体，记忆类型固定为 `SOLUTION`。新增结构扩展表：

```text
conclusion_card
├── memory_id
├── problem_id
└── structured_payload_json
```

候选阶段将结构化数据保存在现有候选记忆机制中；用户确认时，在同一数据库事务内完成：

1. 创建正式 `SOLUTION` 记忆。
2. 创建 `conclusion_card` 扩展记录。
3. 生成全文检索内容。
4. 按卡片自己的选择决定是否进入 Embedding。
5. 建立项目、问题、决策和相关记忆的图谱关系。

### 7.5 结论卡片字段

```text
标题
关联问题编号，可显式为 null
问题描述
最终结论
根本原因
适用条件[]
不适用条件[]
证据[]
已验证结果[]
失败方案[]
不要重复[]
重新尝试条件[]
下一步[]
关键词[]
标签[]
重要度 1-5
重要度评估理由
是否允许云端嵌入
解决时间
```

必填字段：

- 问题描述
- 最终结论
- 根本原因
- 证据
- 已验证结果

所有数组必须显式传递，无内容时传空数组。失败方案必须同时说明方案和失败原因；每条“不要重复”应尽量对应明确的“重新尝试条件”。

## 8. 状态机设计

### 8.1 项目文档状态机

```text
NOT_INITIALIZED
  -> DRAFT_PENDING_REVIEW
  -> DRAFT_PARTIALLY_APPROVED
  -> DRAFT_ALL_APPROVED
  -> PROMOTING
  -> ACTIVE

ACTIVE
  -> SYNC_PENDING
  -> ACTIVE

ACTIVE
  -> FORMAT_ERROR
  -> REPAIR_PENDING
  -> ACTIVE

ACTIVE
  -> CONFLICT
  -> 用户或AI基于最新版本重新提交
  -> ACTIVE
```

### 8.2 正式状态判定

只有同时满足以下条件才判定为 `ACTIVE`：

1. 五份正式文件全部存在。
2. 文件名和 `documentType` 一一匹配。
3. YAML 可以解析且 `schemaVersion` 受支持。
4. 每份文件正文可读取。
5. 数据库镜像可以通过同步或恢复达到一致。

草稿与一套完整有效的正式文件并存时，正式文件优先。残留草稿显示提示并允许用户删除，但不得参与项目交接、FTS、Embedding、最近记忆或图谱。

### 8.3 草稿审核状态机

```text
待审核
  -> 用户批准
  -> 已批准

已批准
  -> 用户编辑、AI更新或版本冲突合并
  -> 待审核

五份均已批准
  -> 自动晋升
  -> 删除初始化草稿
```

AI 在审核期间可以根据后续项目工作更新草稿。更新后必须撤销对应文件的批准状态，并在界面标明变化原因。

## 9. MCP 工具设计

所有工具参数必须显式传递，不设置业务默认值。每个工具只承担一个业务动作，不使用布尔标志在同一个工具中切换创建、更新、删除等模式。

### 9.1 MCP 服务身份与工具路由

MemStack MCP 服务使用稳定的服务标识 `memstack`。AI 提示词、连接配置和客户端适配器必须先锁定该服务，再选择其提供的工具；不得仅凭相似工具名调用其他 MCP 服务。

服务内部工具名保持单一业务语义，不重复添加 `memstack_` 前缀：

```text
服务标识：memstack
服务内工具名：project_handoff_get
逻辑完整名称：memstack.project_handoff_get
```

不同 AI 客户端可能使用不同的实际工具名称。客户端适配器必须将逻辑完整名称转换成目标客户端能够识别的名称，提示词预览、复制内容和安装内容均使用转换后的结果。MCP 服务名、逻辑工具名和客户端实际工具名应分别建模。

### 9.2 `project_handoff_get`

职责：读取、校验和组装当前工作空间的项目交接上下文。

建议显式参数：

```text
workspace_path
context_max_chars
active_decision_max_count
current_status_max_chars
active_problem_max_count
resolved_problem_max_count
recent_changelog_max_count
related_conclusion_card_max_count
conclusion_card_max_chars
```

处理顺序：

1. 规范化并校验工作空间路径。
2. 解析工作空间绑定项目。
3. 注册当前会话的目录监听。
4. 检查正式文件、草稿、数据库镜像和校验和。
5. 必要时执行本地到数据库的补同步，或从数据库恢复缺失文件。
6. 按显式预算返回项目上下文。
7. 同时返回初始化、格式错误、冲突、只读和未同步状态。

交接内容固定包含：

- 完整 Context，但受字符预算限制。
- 当前有效决策。
- 完整 Current Status，但受字符预算限制。
- 全部或预算内的当前问题。
- 少量近期已解决问题。
- 近期 Changelog。
- 与当前状态和当前问题相关的结论卡片。

### 9.3 `project_document_draft_create`

职责：项目未初始化时一次创建五份真实草稿。

要求：

- 调用方显式提交五种文档类型及完整内容。
- 校验五份文件齐全、类型唯一、YAML 正确。
- 已存在初始化草稿时返回现有草稿，不重复创建。
- 已存在完整正式文档时拒绝创建初始化草稿。
- 文件和草稿表均写入成功后才返回成功。
- 草稿不进入任何正式检索通道。

### 9.4 `project_document_draft_update`

职责：更新一份初始化草稿。

建议显式参数：

```text
workspace_path
document_type
expected_version
content
change_reason
```

成功后递增版本并将该文档状态设为待审核。

### 9.5 `project_document_batch_update`

职责：一次提交多份正式项目文档的关联变化。

每项更新至少包含：

```text
document_type
expected_version
content
change_summary
```

执行要求：

1. 先校验全部文档类型、版本、YAML 和正文。
2. 任意一项冲突时不写入任何一项。
3. 保存每份文档唯一上一版安全快照。
4. 写入本地文件并同步数据库镜像。
5. 返回每份文档的新版本和校验和。
6. 不允许静默覆盖监听器刚同步的用户修改。

### 9.6 `conclusion_card_candidate_submit`

职责：提交一张结论卡片候选。

要求：

- 所有结构化字段显式传递。
- 记忆类型固定为 `SOLUTION`，调用方不能借此工具创建其他记忆类型。
- AI 必须展示重要度及评估理由，用户可以在候选界面修改。
- 是否允许云端嵌入由卡片自身字段决定，不继承项目文档设置。
- 返回候选 ID，供 `04_PROBLEMS.md` 的已解决摘要关联。

### 9.7 工具契约同步

实现 MCP 工具时同步修改：

- MCP 调度和参数解析。
- 工具列表契约。
- 输入 JSON Schema。
- 输出结构和错误码。
- 只读令牌权限声明。
- MCP 工具级单元测试和契约测试。

重点检查现有文件：

- `rust/crates/memory-mcp/src/dispatch.rs`
- `contracts/mcp-tools-list.json`

## 10. 桌面端命令与服务职责

桌面端命令应按单一职责拆分，具体名称实施时匹配现有 Tauri 命名风格。至少需要覆盖以下动作：

- 读取初始化草稿列表。
- 读取单份草稿内容。
- 保存单份草稿编辑。
- 批准单份草稿。
- 撤销单份草稿批准。
- 删除残留初始化草稿。
- 执行五份草稿晋升。
- 读取正式文档同步状态。
- 自动修复指定文档。
- 读取和更新项目文档 Embedding 设置。
- 生成指定 AI 客户端的提示词配置预览。
- 安装用户已确认的提示词配置。

不得使用 `mode`、`action`、`force` 等标志参数让一个命令同时执行多个不同业务动作。

## 11. 初始化与审核流程

### 11.1 首次进入项目

1. AI 调用 `project_handoff_get`。
2. 工具返回 `NOT_INITIALIZED`。
3. AI 检查仓库中的项目说明、技术栈、配置、架构和当前任务。
4. AI 生成五份完整草稿，无法确认的事实写入“待确认”。
5. AI 调用 `project_document_draft_create`。
6. MemStack 显示五份草稿列表。
7. 当前项目任务继续执行，不等待用户立即完成审核。

### 11.2 用户审核

1. 用户点击一份草稿查看内容。
2. 用户可以直接编辑并保存。
3. 用户点击“批准”后记录批准版本。
4. 用户依次审核剩余文件。
5. 编辑已批准草稿时自动撤销批准。
6. 第五份草稿批准后自动触发晋升，不再显示第二次总确认。

### 11.3 跨窗口恢复审核

AI 窗口关闭或 MCP 会话结束不会删除草稿。下次进入同一工作空间时，`project_handoff_get` 返回已有草稿及审核状态，MemStack 直接恢复审核界面，不重新生成五份内容。

## 12. 草稿晋升与崩溃恢复

文件系统和 SQLite 无法组成真正的跨介质原子事务，因此必须设计可恢复流程，不得假设五次文件写入天然原子。

### 12.1 晋升步骤

1. 读取五份草稿的当前版本。
2. 确认五份状态均为已批准，且 `approved_version` 等于当前 `version`。
3. 再次校验文件名、YAML、类型和正文。
4. 建立晋升操作记录，状态设为进行中。
5. 在 `.memstack` 同磁盘暂存五份正式文件。
6. 使用同文件系统原子替换逐份写入正式位置。
7. 更新五份正式文档数据库镜像。
8. 将晋升操作标记为完成。
9. 删除 `.memstack/drafts/initialization/`。
10. 清理内部暂存内容。

### 12.2 恢复规则

- 五份正式文件完整且有效：以正式文件为准，补同步数据库，清理或提示处理残留草稿。
- 正式文件只写入一部分：读取晋升记录和已批准草稿，继续补齐，不把残缺集合暴露给项目交接。
- 正式文件完整但数据库事务未完成：以本地文件补写数据库镜像。
- 数据库存在正式镜像但正式文件缺失：从镜像恢复文件。
- 草稿和数据库草稿镜像不一致：以磁盘草稿为准同步数据库，但已批准版本发生变化时撤销批准。

## 13. 文件监听与同步

### 13.1 监听范围

- 只监听当前 MCP 会话对应工作空间的 `.memstack`。
- 不监听其他项目。
- 不扫描整台机器。
- 会话结束后释放该会话的监听引用。
- 多个会话指向同一工作空间时使用引用计数复用监听器，最后一个会话结束后停止。

### 13.2 事件处理

监听器需要识别：

- 正式文件创建或修改。
- 正式文件删除。
- 初始化草稿修改。
- 文件重命名。
- YAML 格式错误。
- MCP 自身写入产生的回环事件。

使用规范化路径、内容校验和和短期写入标识抑制自身写入回环，不能只依赖事件时间戳。

### 13.3 手动修改同步

用户在外部编辑器保存正式文件后：

1. 等待文件写入稳定，避免读取编辑器的中间状态。
2. 解析 YAML 和正文。
3. 校验文件名与文档类型。
4. 计算校验和。
5. 与数据库当前校验和比较。
6. 保存上一版安全快照。
7. 更新数据库镜像和版本。
8. 按项目设置更新 FTS 和可选 Embedding。

### 13.4 离线补同步

监听器不是唯一一致性保障。每次 `project_handoff_get` 都必须重新比较五份文件与数据库校验和，发现离线修改或漏失事件后执行补同步。

## 14. 并发控制与冲突处理

### 14.1 乐观锁

所有 AI 发起的草稿更新和正式文档更新都必须提交 `expected_version`。服务端版本不一致时返回冲突，包括：

- 当前版本
- 当前校验和
- 当前内容或允许读取当前内容的引用
- 冲突文档类型

AI 读取最新内容、重新合并后再次显式提交。禁止自动使用最后写入者覆盖前一个修改。

### 14.2 批量更新一致性

重大问题解决通常同时影响三份文档，因此批量更新必须先完成全部校验。任意文档冲突时，整个批次拒绝，避免状态、问题和变更日志互相矛盾。

文件系统写入中途失败时进入可恢复同步状态。恢复完成前向调用方返回明确的未完全同步结果，不返回普通成功。

## 15. 格式错误与自动修复

### 15.1 错误处理原则

发现 YAML 错误时不得立即用数据库内容覆盖用户文件。界面展示：

- 出错文件。
- 解析错误位置和原因。
- 当前文件是否仍可提取正文。
- 数据库安全快照是否可用。
- “自动修复”按钮。

### 15.2 自动修复顺序

1. 保留可以识别的正文。
2. 根据文件名恢复正确的最小 YAML。
3. 重新解析并校验。
4. 保存修复前内容为唯一上一版安全快照。
5. 写回文件并同步数据库。

只有文件缺失或正文无法可靠提取时，才允许从数据库镜像恢复完整文件。自动修复必须针对单个明确文件，不设置批量或强制模式标志。

## 16. 项目文档的更新规则

### 16.1 会话开始

每个有本地工作空间的新会话只调用一次 `project_handoff_get`。工具调用失败不重复高频重试，不阻断当前工作。

### 16.2 任务结束检查

AI 在每次实际项目任务结束前执行一次项目记忆检查。只有发生以下有意义变化时才更新：

- 稳定项目事实发生变化。
- 产生或替代项目决策。
- 当前阶段、进行中事项、阻塞项、指标或下一步发生变化。
- 新增、推进或解决项目问题。
- 产生值得后续会话知道的重要结果。

普通格式调整、无行为变化的小改动、临时命令输出不写入项目文档。

### 16.3 重大问题解决

问题满足结论卡片条件后立即执行：

1. 更新 `03_CURRENT_STATUS.md`。
2. 将问题从 `04_PROBLEMS.md` 当前区域移动到已解决区域。
3. 在 `05_CHANGELOG.md` 追加变化。
4. 通过一个 `project_document_batch_update` 提交三份文档。
5. 调用 `conclusion_card_candidate_submit` 提交候选。

结论卡片被用户拒绝时，不回退三份项目文档，因为问题已解决属于项目事实，候选是否进入长期经验库属于另一个决策。

## 17. 重大问题判定规则

生成结论卡片必须先同时满足：

1. 问题已经解决。
2. 至少存在一项可以验证的证据。

再满足以下任意一项：

- 找到明确根因。
- 解决方案未来可复用。
- 存在容易被重复尝试的失败路径。
- 对架构、性能、稳定性或数据安全影响明显。
- 经历多轮排查或多种尝试。

未解决的猜测、没有证据的判断、一般性代码修改不得生成结论卡片。

## 18. 重要度评估

AI 在提交候选前必须显示重要度和理由，用户可以修改。

建议规则：

- `1`：局部且短期有效，复用价值很低。
- `2`：一般问题，有有限参考价值。
- `3`：可复用的问题解决经验。
- `4`：影响明显、根因清晰或包含重要失败路径。
- `5`：涉及核心架构、安全、核心数据、重大稳定性或重大性能结论。

普通重大结论通常评估为 `4`，但这不是代码默认值。工具调用仍必须显式传递最终数值和评估理由。

## 19. Embedding 与隐私

### 19.1 项目文档

- 项目级开关默认关闭。
- 用户主动开启时提示五份文档内容可能发送给当前 Embedding 模型服务。
- 关闭时仍可保存 SQLite 镜像和本地全文检索，具体索引范围复用现有离线能力。
- 开关变化后按现有索引任务机制补建或移除向量索引。

### 19.2 结论卡片

- 不继承项目文档开关。
- 每张候选卡片显式选择是否允许云端嵌入。
- 用户确认前可以修改。
- 未允许时不得调用远程 Embedding 服务。

## 20. AI 全局提示词设计

### 20.1 提示词职责

全局提示词只保留稳定的工作流程：

1. 只对明确的本地工作空间启用。
2. 项目记忆操作只能使用服务标识为 `memstack` 的 MCP 服务。
3. 新会话开始调用 `memstack` 服务提供的 `project_handoff_get`。
4. 未初始化时生成五份草稿并交由用户审核。
5. 禁止普通文件工具直接修改正式项目文档。
6. 任务结束前检查有意义变化并通过 `memstack` MCP 批量更新。
7. 重大问题解决后更新三份文档并通过 `memstack` MCP 提交结论卡片候选。
8. 禁止使用其他 MCP 服务中名称或用途相近的工具代替 MemStack 工具。
9. MCP 不可用或只读时继续任务并提示未同步。
10. 纯聊天、无工作空间和未解决推测不初始化、不生成结论卡片。

文档模板、字段枚举、校验规则和工具 JSON Schema 不应全部复制进全局提示词，应由 MCP 工具描述和 MemStack 工作流提供，减少不同客户端配置漂移。

通用提示词使用 `memstack.工具名` 表达逻辑归属。为目标客户端生成预览、复制文本或安装内容时，适配器必须将其转换为该客户端实际识别的工具名称。

### 20.2 安装流程

MemStack 为每种受支持的 AI 客户端提供独立适配器：

1. 检测客户端配置位置。
2. 读取现有配置。
3. 确认 `memstack` 服务标识及该客户端实际暴露的工具名称。
4. 生成目标提示词片段。
5. 显示完整提示词、目标文件、现有内容与目标内容的差异。
6. 提供“复制提示词”和“安装”操作。
7. 用户点击安装后才写入。
8. 写入前保存一份可恢复备份。
9. 安装完成后显示验证结果。

不同客户端的全局提示词文件路径、格式和优先级不同，必须由适配器隔离，禁止通过一个模式参数在同一函数中分支处理所有客户端。

对于不支持自动安装、无法确定配置路径或用户希望手动维护配置的客户端，仍必须允许查看并复制完整提示词。复制内容和安装内容必须来自同一份生成结果，避免两种配置方式产生行为差异。

## 21. 桌面端界面计划

### 21.1 项目记忆入口

在现有项目详情或工作空间相关界面增加“项目文档”入口，展示：

- 初始化状态。
- 五份文档状态。
- 最后同步时间。
- 文件冲突或格式错误。
- Embedding 状态。
- 当前活动会话监听状态。

### 21.2 草稿审核页

布局至少包含：

- 左侧五份文件列表和审核状态。
- 右侧 Markdown 内容查看与编辑区。
- 保存、批准、撤销批准操作。
- 内容变化原因和版本信息。
- 晋升进度及错误恢复提示。

第五份批准后直接开始创建正式文件。创建过程中禁用重复批准操作，但不得阻塞用户切换到应用其他功能。

### 21.3 正式文档页

- 内容只读。
- 支持刷新和打开文件所在位置。
- 显示同步版本、校验和摘要和最后同步时间。
- 格式错误时显示修复入口。
- 文件缺失但可恢复时显示恢复状态。
- 残留草稿存在时显示查看和删除入口。

### 21.4 结论卡片候选页

复用现有候选确认交互，并增加结构化字段编辑：

- 必填字段校验。
- 数组项增删和排序。
- 重要度评估及理由。
- Embedding 选择。
- 问题编号和项目关联。
- 确认、拒绝操作。

### 21.5 AI 连接页的全局提示词入口

在现有“连接 AI”页面中，每个 AI 客户端连接区域必须分别展示：

- MemStack MCP 连接状态。
- MemStack 全局提示词配置状态。
- MCP 服务标识 `memstack`。
- 当前提示词版本和待更新状态。

MCP 已连接不代表 AI 已获得 MemStack 工作流提示词，页面不得把两者合并成一个“已配置”状态。

连接区域增加“查看全局提示词”按钮。点击后使用抽屉或弹窗展示：

- 当前适用的 AI 客户端。
- MCP 服务标识 `memstack`。
- 提示词模板版本。
- 该客户端实际使用的 MemStack 工具名称。
- 完整、只读的最终提示词。
- 配置目标文件，仅在能够安全识别时显示。
- 当前配置与目标配置的差异入口。

提示词查看区域提供以下独立操作：

- `复制提示词`：复制当前展示的完整最终提示词。
- `查看安装差异`：只读取并展示目标配置变化，不执行写入。
- `安装`：用户确认后写入目标配置。
- `重新生成`：服务标识、工具名称、客户端配置或模板版本变化后生成新预览。

交互要求：

- 复制成功或失败必须显示明确反馈。
- 提示词正文保持只读，防止用户误以为编辑后的内容仍是 MemStack 官方模板。
- 未连接 MCP 时可以查看通用提示词；只有成功解析客户端工具命名空间后，才标记为“可直接使用的客户端适配提示词”。
- 不支持自动安装的客户端隐藏或禁用安装操作，但保留查看和复制。
- 提示词不得包含访问令牌、数据库地址、用户私有路径或其他敏感信息。
- 复制、查看差异和安装必须使用同一提示词版本和同一生成结果。
- 重复安装必须幂等，并保留用户配置中与 MemStack 无关的内容。

## 23. 分阶段实施计划

### 阶段 0：代码基线核查

目标：在写代码前确认可复用能力和真实改动点。

任务：

1. 阅读项目、工作空间绑定和权限模型。
2. 阅读普通记忆、候选记忆、确认流程和乐观锁。
3. 阅读数据库迁移规范和测试数据库创建方式。
4. 阅读 FTS、Embedding 和图谱写入流程。
5. 阅读 MCP 工具注册、契约生成和错误码约定。
6. 阅读 Tauri command、前端状态管理、路由和候选审核界面。
7. 确认仓库指定的格式化、测试、lint 和构建命令。

交付结果：最终字段命名、模块位置和迁移编号清单。

### 阶段 1：领域模型与数据库迁移

目标：建立项目文档和结论卡片的数据基础。

任务：

1. 增加文档类型、审核状态、同步状态模型。
2. 增加正式文档表和唯一上一版快照字段。
3. 增加草稿表和批准版本字段。
4. 增加项目文档 Embedding 设置。
5. 增加结论卡片结构扩展表。
6. 增加唯一约束、必要索引和迁移测试。

验收：旧数据库可以平滑升级，新建数据库结构完整，唯一约束生效。

### 阶段 2：文件格式、路径与校验服务

目标：集中管理 `.memstack` 文件系统规则。

任务：

1. 建立路径常量和文档类型到文件名的唯一映射。
2. 实现工作空间路径规范化和越界保护。
3. 实现 YAML 解析、正文提取和 schema 校验。
4. 实现内容规范化和校验和计算。
5. 实现安全写入、同盘暂存和原子替换。
6. 实现 Git 本地排除规则的幂等维护。

验收：错误文件名、类型不匹配、非法 YAML、路径逃逸和重复类型均被拒绝。

### 阶段 3：草稿创建与审核

目标：完成可跨窗口恢复的初始化审核闭环。

任务：

1. 实现草稿创建和重复创建保护。
2. 实现草稿读取和单份更新。

## 24. 测试矩阵

### 24.1 初始化

- 没有 `.memstack` 时返回未初始化。
- 已有草稿时恢复原草稿，不重复生成。
- 正式文档存在时不创建草稿。
- 五份草稿缺一份时拒绝整体创建。
- YAML 类型和文件名不匹配时拒绝。
- 用户编辑已批准草稿后自动撤销批准。
- 第五份批准后自动晋升。

### 24.2 晋升与恢复

- 五份文件全部成功创建。
- 写入第一个文件后崩溃可以恢复。
- 文件完整但数据库未提交可以补同步。
- 正式文件和草稿并存时正式集合优先。
- 只有部分正式文件时不会输出残缺交接内容。
- 晋升成功后删除初始化草稿。

### 24.3 监听与同步

- 用户手动修改正式文件后更新数据库。
- MCP 自身写入不会重复增加版本。
- 编辑器连续多次文件事件只处理稳定内容。
- 离线修改在下次交接时补同步。
- 文件缺失时从镜像自动恢复。
- YAML 错误时不自动覆盖用户正文。
- 自动修复保留正文并恢复正确 YAML。

### 24.4 并发

- 两个 AI 基于同一版本修改，只有第一个成功。
- 第二个收到完整冲突信息后可以重新合并。
- 三份文档批量更新发生一个冲突时全部拒绝。
- 多会话监听同一工作空间时不重复启动底层监听器。
- 最后一个会话结束后停止监听。

### 24.5 权限与降级

- 只读 Token 可以交接读取但不能更新。
- MCP 不可用时任务继续并显示未同步。
- 工作空间未绑定项目时不初始化。
- 没有本地工作空间时不初始化。
- 路径逃逸和符号链接越界被拒绝。

### 24.6 Embedding

- 项目文档开关默认关闭。
- 未开启时不调用远程 Embedding。
- 开启前显示隐私提示。
- 结论卡片使用自身开关，不继承项目设置。
- 用户拒绝候选时不产生向量。

### 24.7 结论卡片

- 缺少必填字段时拒绝提交。
- 空数组被显式保存。
- 问题编号允许显式为 `null`。
- 重要度和理由可以在确认前修改。
- 确认后创建 `SOLUTION` 和记忆扩展记录。
- 拒绝卡片不回退三个项目文档。
- 项目交接能召回与当前问题相关的卡片。

### 24.8 提示词安装

- 多个 MCP 提供相似工具时，生成的提示词明确选择 `memstack` 服务。
- 不同客户端预览中显示各自实际可识别的工具名称。
- “连接 AI”页面分别显示 MCP 连接状态和提示词配置状态。
- 可以打开完整提示词查看界面。
- 复制内容与当前预览内容完全一致。
- 复制成功和失败均有反馈。
- 复制内容不包含 Token、数据库地址和用户私有路径。
- 不支持自动安装的客户端仍可查看和复制。
- 只预览时不写入配置。
- 点击安装后只修改目标片段。
- 保留用户现有无关配置。
- 写入失败时可从备份恢复。
- 重复安装保持幂等。

## 25. 验收标准

功能完成必须同时满足：

1. 新项目可以生成五份真实草稿并逐份审核。
2. 草稿跨 AI 窗口永久保留，正式创建成功后删除。
3. 正式项目文档只有一套，并以本地 Markdown 为事实来源。
4. 用户手动修改、AI 更新、离线修改和文件缺失均能正确同步或恢复。
5. 多 AI 并发不会静默覆盖。
6. 新会话可以通过一次 MCP 调用获得受预算控制的项目交接内容。
7. 重大问题解决后能够提交结构化结论卡片候选。
8. 候选经用户编辑确认后进入正式记忆、FTS、可选 Embedding 和图谱。
9. 默认不会将五份项目文档发送到云端 Embedding 服务。
10. MCP 或项目记忆故障不会阻断当前项目任务，并会明确提示未更新。
11. 多 MCP 环境下，AI 提示词明确绑定服务标识为 `memstack` 的 MCP，不依赖模糊工具名称选择服务。
12. “连接 AI”页面可以查看并复制当前客户端适配后的完整全局提示词。
13. MCP 连接状态与提示词配置状态分别展示，不产生“连接成功即提示词已安装”的误导。
14. 提示词配置只有在用户查看差异并点击安装后才写入。
15. 现有项目、记忆、候选确认和 MCP 工具没有行为回归。

## 26. 风险与控制措施

### 26.1 文件与数据库跨介质事务

风险：文件已经写入但数据库事务失败，或数据库成功但文件替换中断。

控制：本地文件作为事实来源、晋升操作记录、同盘暂存、原子替换、唯一上一版快照和下次交接补同步。

### 26.2 文件监听事件不可靠

风险：系统合并或丢失事件，编辑器产生多次中间事件。

控制：监听只用于及时同步，每次项目交接仍执行完整校验和比对。

### 26.3 AI 生成错误事实

风险：AI 将推测写入 Context 或决策。

控制：初始化逐份审核；不确定内容进入“待确认事实”；正式创建前必须用户批准。

### 26.4 全局提示词过长或漂移

风险：不同 AI 客户端维护不同副本，行为逐渐不一致。

控制：提示词只保存稳定工作流，详细模板和结构由 MCP 契约提供；通过客户端适配器统一生成。

### 26.5 项目文档体积持续增长

风险：决策、已解决问题和 Changelog 长期增长，交接占用过多上下文。

控制：交接时显式传入数量和字符预算；Current Status 只保存当前状态；已解决问题只保留压缩摘要；详细经验进入结论卡片。

### 26.6 隐私外发

风险：项目事实或问题细节被发送到远程 Embedding 服务。

控制：项目文档默认关闭云端 Embedding；结论卡片逐张显式选择；界面显示清晰提示。

## 27. 推荐实施顺序结论

必须先完成领域模型、数据库、文件一致性和草稿状态机，再实现界面和提示词安装。提示词只能触发工作流，不能替代底层约束。

推荐主路径：

```text
模型与迁移
  -> 文件校验与安全写入
  -> 草稿审核与晋升
  -> 正式同步与监听
  -> MCP 项目交接
  -> 结论卡片
  -> 桌面端完整交互
  -> 提示词显示安装
  -> 端到端回归
```

五份项目文档解决“当前项目是什么、为什么这样做、现在进行到哪里”；结论卡片解决“重大问题最终如何被证明和解决”。两者必须关联，但保持独立生命周期和存储模型。
